## 사용 방법

### 1. 처음 한 번만 하는 준비

```bash
git clone <저장소 주소>
cd sw-engineering-16
```

`docs/` 폴더에 참고 자료를 넣는다 (자세한 내용은 [docs/README.md](docs/README.md)).

| 파일 | 넣을 위치 | 필수 |
|---|---|---|
| 팀 PPT PDF (User_Requirement.pdf) | `docs/User_Requirement.pdf` | 필수 |
| 강의자료 5장 (시퀀스 다이어그램) | `docs/chap5.pdf` | 선택 |
| Claude Docs 초안 (Markdown으로 내려받기) | `docs/drafts/` | 4-2, 6, 18-1, 18-2 담당자 |

### 2. 기능 하나 작성하는 순서

요구사항 → 시퀀스(Mermaid) → 클래스 파일 → GLOSSARY → 유스케이스 → 체크리스트 확인 → main에 push

브랜치와 PR은 쓰지 않는다. 모두 main에서 작업하고 승인 없이 바로 push한다.

1. **최신 내용 받기**
   ```bash
   git pull
   ```
2. **템플릿 복사**
   ```bash
   cp templates/requirement.md requirements/req-14.md
   cp templates/sequence.md sequence/seq-14.md
   ```
3. **요구사항 작성** — Action은 "어느 DB에서 무엇을 조회해 무엇을 한다", 모든 조건에 else 동작, 다른 기능 실행·전달 표현 금지.
4. **시퀀스 작성** — Mermaid로. 시작 메시지는 사람→UI, 시각→`시간`, 데이터 변화→Found Message. 아래에 Action ↔ 메시지 대응표.
5. **클래스 파일 수정** — 메시지를 받는 클래스 파일에 연산과 사용처를 추가. **새 연산을 만들기 전에 그 클래스 파일에 쓸 수 있는 연산이 있는지 먼저 확인**한다 (CONVENTIONS 6.4).
6. **GLOSSARY 등록** — 새 용어·객체·enum이 생겼으면 `추가` 상태로 등록.
7. **유스케이스·README 갱신** — `usecase/usecase.md`와 아래 담당 표의 상태를 바꾼다.
8. **체크리스트 확인** — [CHECKLIST.md](CHECKLIST.md)의 항목을 확인한다.
9. **커밋·push**
   ```bash
   git add .
   git commit -m "[req-14] 음주량 기반 술 추가 요구사항·시퀀스 작성"
   git pull
   git push
   ```
   push 직전의 `git pull`은 그사이 다른 사람이 올린 내용을 합치기 위한 것이다. 같은 파일의 같은 줄을 고쳐 충돌이 나면, 충돌 난 파일을 열어 정리한 뒤 다시 커밋하고 push한다.

> 공통 객체(귀가시간계산, 테이블출석현황 등)의 연산을 바꾸면 그 연산을 쓰는 기능 담당자 모두에게 알린다.

### 3. 다이어그램 확인하기

- GitHub에서 `sequence/seq-번호.md`를 열면 Mermaid가 바로 그림으로 보인다.
- 로컬에서는 VS Code + "Markdown Preview Mermaid Support" 확장, 또는 [mermaid.live](https://mermaid.live)에 코드를 붙여 넣어 확인한다.
- 그림이 안 나오면 문법 오류다. push 전에 꼭 확인한다.

### 4. Claude Code로 작업하기

저장소 폴더에서 Claude Code를 열면 `CLAUDE.md`를 자동으로 읽고 규칙대로 작업한다. 아래 프롬프트를 복사해서 `○○` 부분만 바꿔 쓴다.

#### ① 처음 한 번: 전체 기능 분석 (파일 수정 없음)

```
CLAUDE.md, CONVENTIONS.md, GLOSSARY.md를 먼저 읽어줘.
그다음 docs/User_Requirement.pdf의 기능 1~20을 전부 읽고 아래 세 가지를 표로 정리해서 보여줘. 아직 파일은 고치지 마.

1. 공통 객체 후보: 두 개 이상의 기능이 같은 일을 하는 부분 (하는 일, 쓰는 기능 번호, 제안 이름, 제안 연산과 매개변수 자료형)
2. 통일할 DB 연산: 여러 기능에서 같은 DB를 같은 목적으로 조회·저장하는 부분 (DB, 제안 연산 이름, 쓰는 기능)
3. 동의어: 같은 뜻인데 다르게 쓴 표기 (발견한 표기들, 제안 대표 용어, 나온 기능 번호)

GLOSSARY에 이미 있는 것은 "있음"으로 표시해줘.
```

결과를 팀이 같이 보고 정한 뒤:

```
1번에서 ○○, ○○를 공통 객체로 확정하고, 2·3번은 전부 반영해서 GLOSSARY.md를 수정해줘.
공통 객체는 classes/ 파일도 만들어줘.
```

#### ② 기능 하나 작성

```
docs/User_Requirement.pdf의 ○번 '기능명'을 저장소 규칙대로 작성해줘.
(초안이 있으면: docs/drafts/○○.md의 초안을 참고해서 옮겨줘.)

1. requirements/req-○.md와 sequence/seq-○.md를 templates/ 형식으로 작성
2. 시퀀스 메시지를 받는 클래스 파일에 연산과 사용처 추가. 새 연산을 만들기 전에 기존 연산을 재사용할 수 있는지 먼저 확인
3. usecase/usecase.md와 README.md 담당 표 갱신
4. GLOSSARY에 없는 용어·객체·enum이 필요하면 만들기 전에 나한테 먼저 물어봐
5. 끝나면 CHECKLIST.md 체크리스트 중 통과 못 한 항목과, 원문에서 애매해서 판단이 필요한 부분을 알려줘
```

#### ③ 규칙 바꾸기

```
CONVENTIONS.md의 ○○ 규칙을 △△로 바꾸고 싶어. 이유는 □□야.
바꾸면 이미 작성된 파일 중 어떤 걸 고쳐야 하는지 먼저 알려주고,
내가 확인하면 CONVENTIONS.md, 영향받는 파일을 함께 고치고 FEEDBACK.md에도 기록해줘.
```

#### ④ push 전 점검

```
아직 push하지 않은 변경 파일을 CONVENTIONS.md와 GLOSSARY.md 기준으로 점검해줘.
쓰지 않는 표기, 공백 있는 객체 이름, else 없는 조건, 다른 기능 전달 표현,
사용처가 틀린 연산, 다른 클래스와 겹치는 메서드 이름, Mermaid 문법 오류를 찾아서 목록으로 알려줘. 고치지는 말고.
```

### 5. 규칙을 바꾸고 싶을 때

규칙은 작업하면서 바꿀 수 있다. 다만 혼자 바꾸지 않는다.

1. 바꿀 내용과 이유를 정리한다 (위 프롬프트 ③ 사용 가능).
2. CONVENTIONS.md 또는 GLOSSARY.md를 고쳐 push한다.
3. **팀원 전원에게** 바꾼 내용과 이유를 알린다.
4. 교수님·팀 피드백이 근거면 [FEEDBACK.md](FEEDBACK.md)에 한 줄 추가한다.
5. 이미 작성된 파일 중 영향받는 것도 같은 커밋에서 고친다.

### 6. 자주 하는 실수

| 실수 | 바르게 |
|---|---|
| "기능 7에서 사용한다", "기능 9로 전달" | 각 기능은 독립적으로 쓴다. 다른 기능 언급 금지 |
| Side effects에 "다음 기능 실행" | DB 용량 증가, 알림 발송, 데이터 보관 기간 같은 시스템 영향 |
| `학생 UI`, `모임 DB` | `학생UI`, `모임DB` (공백 없이) |
| `S: 시스템`, `○○Controller` | 담당 객체 이름 (기능명에서 공백 제거) |
| 모임DB가 첫 메시지를 보냄 | 사람→UI, 시각→`시간`, 데이터 변화→Found Message |
| `ceil(n/4)` | "n을 4로 나누고 올림한 값" |
| `환불`, `동석자` | `환급`, `같은 테이블 출석 학생` (GLOSSARY 9장) |
| 매개변수 이름만 씀 | `학생ID: int`처럼 자료형까지 |
