# 교수미팅 정리 (11/10)

## 1. 요구사항 명세서(SRS) 작성 지침

### 구체적인 알고리즘 기술 (외주 개발 관점)
- 요구사항은 실제 외주 개발자에게 전달했을 때 추가 질문 없이 코드로 바로 옮길 수 있을 만큼 디테일해야 합니다.
- '하버사인 공식으로 계산한다'와 같이 러프하게 끝내지 말고, 수식과 변수 관계를 상세히 명시해야 합니다.

### 입력(Input)과 소스(Source)의 엄격한 일치
- 계산식에 들어가는 데이터는 반드시 Input/Source에 정의되어 있어야 합니다.

### 상수(Constant)와 변수(Variable)의 구분
- 지구 반경($R = 6,371\text{ km}$), 도로 굴곡 계수($1.3$), 보행/차량 속도 등은 시스템 상숫값(Constant)으로 처리한다고 명시합니다.
- 사용자 위치, 자택 좌표 등 실시간으로 변하는 값만 입력 변수로 처리합니다.

### 가정(Assumption)의 구체화
- "사용자 프로필이 이미 등록되어 있다"고 뭉뚱그리지 말고, 프로필 안에 어떤 필드(나이, 관심사, 선호 음식 등)가 존재하는지 명확히 한정해야 백엔드 연동 시 데이터 누락이 발생하지 않습니다.

## 2. 유스케이스 모델링 지침

### '시간(Time)'은 액터(Actor)가 아님
- 액터는 인간 사용자(학생, 사장님)이거나 독립적인 거대 외부 시스템(결제 게이트웨이, 푸시 서버 등)이어야 합니다.
- 단순 시스템 클럭이나 타임 인터벌은 액터로 둘 수 없으며, 필요하다면 백그라운드 스케줄러(Scheduler) 컴포넌트로 표현하거나 시스템 내부 타이머 이벤트로 처리해야 합니다.

### 유스케이스 명칭에 명확한 '동사' 사용
- 단순 명사형(예: '프로필 기반 대화 주제 카드')은 무엇을 하는 기능인지 알 수 없습니다.
- '프로필 기반 대화 주제 카드 추천', '대화 카드 생성'처럼 명확한 목적 동사를 붙여야 합니다.

### 추천/매칭 기능의 구체적 판정 기준 명시
- 단순 매칭이 아닌 추천 로직이라면, 어떤 데이터(선호도, 연령대, 이전 대화 기록 등)를 기반으로 어떤 조건 분기(if-else)를 거쳐 추천 카드를 뽑아내는지 단계별 규칙이 요구사항에 서술되어야 합니다.

## 3. 클래스 다이어그램 설계 지침

### 학생UI 클래스의 비대화(God Object) 해결
- UI 클래스 하나에 앱 전체의 변수와 어트리뷰트가 수십 개씩 몰려 있는 것은 객체지향 설계 실패입니다.
- 화면/도메인 단위로 클래스를 분할해야 합니다 (예: 학생카드UI, 모임신청UI, 출석UI 등).

### 속성(Attribute)과 파라미터(Parameter)의 엄격한 구분
- 화면에 잠깐 떴다가 사라지는 일회성 데이터(팝업 알림 메시지, 에러 안내 등)는 UI 클래스의 변수(어트리뷰트)로 저장하지 않습니다.
- 메서드의 매개변수(`show(String message)`)로 넘겨주고 끝내야 합니다.
- UI 클래스에 속성으로 보존해야 하는 것은 사용자가 지속해서 변경·선택할 수 있는 상태 데이터(예: 선택 리스트 등)에 한합니다.

### 개별 DB 클래스 남발 금지 및 상속(Generalization) 적용
- '결제DB', '프로필DB', '질문카드DB' 등으로 클래스를 전부 쪼개면 클래스 다이어그램이 난잡해집니다. 이들은 실제 시스템에서 단일 DB 내의 '테이블'에 불과합니다.
- 공통 데이터베이스 인터페이스/저장소 클래스를 두고, 필요 시 상속 구조를 활용하거나 통합 DB 컴포넌트로 단순화해야 합니다.
- 방향선(화살표)을 남발하지 말고, 표준적인 상속(빈 삼각 화살표) 관계를 명확히 표현해야 합니다.

## 4. 시퀀스 다이어그램 설계 지침

### 컴포넌트/라이프라인 네이밍 오류 수정
- 특정 유스케이스 명칭(예: '1인 잔류 테이블 합석', '테이블 출석 현황')을 그대로 라이프라인(컨트롤러/클래스) 이름으로 박지 않아야 합니다.
- 표준적인 : 시스템(System) 단일 컴포넌트를 사용하거나, 역할을 명확히 담은 도메인 객체명(예: Table, Session)을 사용해야 합니다.

### 데이터 획득 흐름의 완결성 (파라미터 인과관계)
- 시스템이 DB에 모임 상태 조회(모임 ID)를 날릴 때, "시스템이 그 모임 ID를 사전에 어떻게 확보했는가?"에 대한 선행 단계가 누락되면 안 됩니다.
- 전체 활성화 목록 조회 $\rightarrow$ 대상 특정 $\rightarrow$ 상세 조회 순으로 데이터 조회 체인을 빈틈없이 연결해야 합니다.

### 비동기 타이머/스케줄러 흐름 정리
- 시간 만료 처리가 필요하다면 시스템이 스케줄러에 종료 시간을 사전 등록(종료 시간 설정)하고, 해당 시점이 도래했을 때 콜백/알림을 받아 후속 로직을 트리거하는 인과적 순서로 배치해야 합니다.
