# 발표용 변환 규칙 (presentation 폴더 전용)

원본 시퀀스 하나를 발표용 유스케이스, 시퀀스, 클래스 3장으로 옮기는 규칙이다. **이 폴더 안에서만 쓴다.** 저장소 규칙(CONVENTIONS.md)과 다른 점은 아래 "CONVENTIONS와 다른 점"에 모았다.

예시: [03/](03/) (3번 친해지고싶은학생알림)

## 0. 기본

- 원본(sequence/, classes/, requirements/)은 고치지 않는다. 고칠 점은 그 기능 폴더 README의 "원본에 맞추려면" 표에 적는다.
- 원본의 **흐름과 메시지는 그대로** 쓴다: 시작 방식, opt/alt/loop 구조, 메시지의 메소드명·매개변수(이름과 타입)·반환값·반환 화살표 이름. 이름에 공백이 있어도 그대로 둔다.
- 바꾸는 것은 **라이프라인**(2장 표)뿐이다.
- 단, 화면에 띄우거나 조건에 쓰는 데이터를 어디서 얻는지 빠져 있으면(빈틈), **메시지를 추가해서** 메운다 (예: 03의 7번 모임정보조회). 그 데이터를 받아야 하는 메시지는 매개변수를 그 데이터로 바꾼다 (예: 03의 8번 모임신청화면표시가 모임정보를 받음). 추가·변경한 메시지는 "원본과 달라진 점" 표에 적는다.
- 권한(알림 권한, 위치 권한, 긴급 연락 동의 등)은 모든 학생이 이미 동의한 것으로 본다. 원본 메모나 조건에 있는 권한 확인은 빼고, 메모에 "권한은 이미 동의한 것으로 본다"고 적는다 (DISCUSSION 안건 14).

## 3. 클래스 그리는 법

**들어가는 클래스**
1. 라이프라인 클래스 (담당 객체 «module», DB, 화면)
2. DB에 붙는 `테이블종류` «enumeration». 값은 이 시퀀스의 DB 메시지가 조회·저장하는 테이블만 적는다 (예: 03의 관심등록, 모임). Found Message의 출처 테이블은 넣지 않는다
3. 화면의 부모 `UI` «abstract»
4. 매개변수·반환에 나온 «dataType» (예: 03의 모임정보)
- DB에는 속성을 쓰지 않는다. 테이블의 칸(컬럼)도 그리지 않는다

**연산·속성**
- 연산은 메시지와 똑같이 쓴다 (이름에 공백이 있어도 그대로). 받는 메시지는 `+`, 자기 호출은 `-`. 매개변수는 자료형만 쓴다 (FEEDBACK #16).
- DB와 화면에는 **이 시퀀스에서 쓰는 연산만** 그린다. 원본 클래스 파일에 같은 일을 하는 연산이 다른 이름으로 있어도 시퀀스 메시지 이름을 따른다.
- 담당 객체의 속성은 원본 클래스 파일(classes/)의 속성을 그대로 쓴다.
- «dataType» 속성은 이 기능에 필요한 것만 쓴다.

**관계**
- 상속(빈 삼각형)에만 방향을 넣고, 나머지는 선만 긋는다 (FEEDBACK #11, 교수님 "상속 말고 방향 넣지 말라").
- 다중성 숫자는 넣지 않는다 (FEEDBACK #30).
- 선은 메시지를 주고받는 클래스끼리, 그리고 «dataType»을 쓰는 클래스와 그 «dataType» 사이에 긋는다.

**검산**: 메시지 수 = 연산 수가 대조표에서 맞아야 한다. 클래스는 7개 안팎이 목표다 (11/11 수업).

## 4. Mermaid 주의

- 클래스 그림의 제네릭은 `List~int~`로 쓴다.
- 스테레오타입은 클래스 안에 `<<module>>`, `<<abstract>>`, `<<enumeration>>`, `<<dataType>>`로 쓴다.
- 담당 객체 라이프라인은 `participant 알림 as 친해지고싶은학생알림 «module»`로 쓴다.
- 연산 이름에 공백이 있으면 GitHub에서 깨지지 않는지 한 번 확인한다.

## 5. CONVENTIONS와 다른 점 (이 폴더에서만)

| CONVENTIONS | 이 폴더 |
|---|---|
| 3장 메시지·연산 이름은 공백 없이 | 원본 메시지 이름 그대로 (공백이 있어도 됨) |
| 5.1 담당 객체 = 기능명 | 기능명 + «module» |
| 5.2 시각으로 시작 → 시간 액터 | 스케줄러 참여자 |
| GLOSSARY 등록 후 사용 | 단계별 화면(모임신청UI 등)·UI·«dataType»(모임정보 등)을 등록 없이 사용 |
| DB는 테이블마다 | DB 하나 + 테이블종류 enum (쓰는 테이블만) || 화살표 없이 선만 (6.3) | 상속만 빈 삼각형 |
| 원본 흐름 그대로 | 빈틈은 메시지를 추가해서 메운다 |
| 요구사항의 권한 조건 | 모두 이미 동의한 것으로 보고 뺀다 |

## 6. 아직 정하지 않은 것

- DB 내용을 한눈에 보이게 할지. 안: DB 상자에 시퀀스 메시지 그대로의 구체 연산과 함께 공통 함수(조회·목록조회·저장·갱신, 첫 매개변수 테이블종류, [class-diagram/draft-restructure.md](../class-diagram/draft-restructure.md) 4.2)를 넣고, 구체 연산이 어느 공통 함수를 어느 테이블로 부른 것인지 메모로 잇는다. 정할 것: 공통 함수를 8개 전부 / 4개 / 쓰는 것만 넣을지
- 테이블종류 enum에 Found Message의 출처 테이블(03이면 신청)도 넣을지
- 스케줄러를 클래스 그림에 넣을지. 보내기만 하면 연산이 없다. 1번처럼 스케줄러가 메시지(타이머등록 등)를 받는 기능을 발표할 때 같이 정한다.
